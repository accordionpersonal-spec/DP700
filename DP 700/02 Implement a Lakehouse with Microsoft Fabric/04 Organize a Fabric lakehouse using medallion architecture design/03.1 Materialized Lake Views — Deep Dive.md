# Materialized Lake Views — Deep Dive
*DP-700 · supplement to "Plan a medallion architecture in Fabric"*

## Is this actually used in industry?
Two-part honest answer:
- **The Fabric feature is new.** Preview at Build 2025 → generally
  available at FabCon Atlanta, March 2026. Few engineers have years of
  Fabric-MLV production scars yet.
- **The concept is 30+ years old and everywhere.** "Materialized view" =
  one of the most battle-tested ideas in data. What's new is bringing it
  to lakehouses with automatic refresh.

## Same idea, different names

| Product | Name for it |
|---|---|
| Oracle (since late 90s) | Materialized views — banks/telecoms still run reporting on them |
| SQL Server | Indexed views (the T-SQL world's version) |
| BigQuery / Redshift | Materialized views |
| Snowflake | Dynamic Tables |
| Databricks | Delta Live Tables — core building block (→ Phase 2 cert) |
| dbt | Incremental models — the manual DIY version |

## The intuition: your bank balance
- Source of truth = append-only **ledger of transactions**.
- Opening the app does NOT sum 10 years of transactions — it reads a
  **precomputed balance**, patched incrementally per new transaction.
- Expensive query → computed once → kept fresh incrementally.
- Same trick behind video view counts, seller ratings,
  "orders this month" tiles: expensive aggregate, read constantly,
  changes slowly.

## The everyday DE version: the Monday 9 AM dashboard
Revenue dashboard, 200 people open it Monday morning.

1. **Regular view** — query reruns per open. 50M rows × 200 people.
   Slow, expensive, everyone angry.
2. **Scheduled rebuild** (what most teams do today) — notebook rebuilds
   a summary table nightly, pipeline schedules it. Works, but:
   - you own the scheduler, alerts, dependency order
   - naive rebuild reprocesses 50M rows when 200k are new
   - one bronze→silver→gold flow = notebook per transform + pipeline
     to order them + schedules + monitoring. Five moving parts.
3. **MLV** — declare the SELECT once. Fabric picks the optimal refresh
   per run: **incremental** (only new/changed rows), **full** (rebuild),
   or **skip** (nothing changed). Tracks dependencies between views and
   refreshes them in the correct order.

## How it works underneath
- Every Fabric table is **Delta** → transaction log records every change.
- **Incremental refresh unlocks only if CDF (change data feed) is
  enabled on the source tables:**
  `ALTER TABLE bronze.orders SET TBLPROPERTIES
  (delta.enableChangeDataFeed = true);`
  Without CDF, Fabric only chooses between **skip** and **full**.
- Unsupported SQL constructs don't block creation — Fabric just falls
  back to full refresh. Force one manually after a correction:
  `REFRESH MATERIALIZED LAKE VIEW silver.sales FULL;`
- Prereqs: **schema-enabled lakehouse** + Fabric Runtime 1.3+.

## What GA (March 2026) added beyond the MS Learn module
- **PySpark authoring** — define MLVs from notebooks via DataFrameWriter
  (for logic SQL can't express). *Currently full refresh only.*
- **Multiple named schedules** — e.g. finance gold refreshes hourly,
  low-priority analytics every 6 hours; each schedule refreshes upstream
  dependencies in order, runs independent views in parallel.
- **Data quality constraints** in the definition:
  `CONSTRAINT valid_sales CHECK (sales_amount > 0) ON MISMATCH DROP`

## Why "lake" versions only appeared in the 2020s
Old data lakes = dumb files, no change tracking → "what's new since
last run?" meant rescanning everything. Delta's transaction log made
incremental refresh feasible → Fabric MLVs, Databricks DLT, and
Snowflake Dynamic Tables all arrived in the same era.

## Tradeoffs (interview-ready)
- **Storage duplication** — result persists as a real Delta table.
- Logic must fit SQL (or now PySpark, with the full-refresh caveat).
- Refresh lag — fresh-on-schedule, not real-time streaming.
- Overkill for trivial transforms where a plain view is fine.

## Interview line
> "I've built this pattern manually — incremental loads orchestrated in
> ADF and Glue. The industry now automates it declaratively: Fabric
> MLVs, Databricks DLT, Snowflake Dynamic Tables."
Shows you understand the **need**, not just the feature.

## Exam triggers
| Question says… | Think… |
|---|---|
| SQL transform, stays current automatically, no scheduling | MLV |
| reruns every query vs. saved + auto-updated | regular view vs. MLV |
| incremental refresh not happening | enable **CDF** on source tables |
| Python/UDF/ML logic in the transform | notebook (or PySpark MLV, full refresh) |
| different refresh frequencies per pipeline | named schedules |
