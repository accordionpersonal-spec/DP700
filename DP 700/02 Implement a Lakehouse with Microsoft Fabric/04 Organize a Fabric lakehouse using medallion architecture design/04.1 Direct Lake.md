# Direct Lake vs. Import — What Happened to "Report Refresh"
*DP-700 · supplement to "Serve gold layer data" (semantic models)*

## ⚡ The simple version (30 seconds)
- **Old way (Import mode):** Power BI keeps a **copy** of the data.
  The scheduled "report refresh" the BI team babysits = re-copying
  data from source into Power BI. Stale between refreshes, 6 AM
  failures, hour-long runs on big models.
- **Direct Lake:** there is **no copy**. The semantic model reads
  gold's Delta files in OneLake directly. New data lands in gold →
  the next query sees it.
- **Refresh doesn't vanish — it shrinks.** Direct Lake still has a
  "refresh," but it's **metadata-only** (called *framing*): update
  the pointer to the latest table version, drop stale columns from
  memory. Seconds, zero data movement — and **automatic by default**.

> One-liner for the BI team:
> **Import = copy + scheduled refresh + babysitting.
> Direct Lake = no copy; refresh becomes an instant, automatic
> pointer update.**

(Terminology flex: reports never refresh — the *semantic model*
refreshes; reports just read it.)

---

## The old world: Import mode
- Semantic model holds a full in-memory **copy** of the data.
- Scheduled refresh = re-import everything from source.
- Pain package: stale numbers between refreshes, refresh failures
  to babysit, long refresh windows as data grows.
- (The other old option, DirectQuery: no copy, always live — but
  every visual fires a query at the source. Slow dashboards.)

## Why Direct Lake needs no copy
- Gold tables are **Delta/Parquet in OneLake** — a columnar format
  the Power BI engine loads natively.
- The model pulls into memory **only the columns the visuals
  actually use**, on demand.
- Same recurring theme as MLVs and shortcuts:
  **Delta-everywhere is the enabler.**

## The fine print: framing
- A Direct Lake "refresh" = **framing**: point the model at the
  latest version of the Delta table + evict stale columns.
- Metadata-only → seconds, not hours.
- **Automatic by default**: new data in the table triggers a
  reframe on its own.

## Where the DE enters this story
- The one good reason to turn auto-update **off**: multi-step loads.
- Pipeline updates `orders`, returns 2 minutes later for the next
  table → auto-reframe could let a dashboard catch gold **mid-load**
  → inconsistent numbers in a meeting.
- Fix: disable auto-update, trigger the reframe as the **final step
  of the pipeline**. Load finishes → reframe → users see one
  consistent snapshot.
- This is a **data engineer's decision**, not a BI one.
  (Good interview line.)

## "Live" — with two asterisks
1. Current-as-of-latest-data, **not a streaming push** — an
   already-open dashboard doesn't repaint by itself; the user
   interacts or reopens. (Auto page refresh = separate feature.)
2. If a query breaks Direct Lake's rules (capacity guardrails,
   certain unsupported features), it silently **falls back to
   DirectQuery** for that query — still live, just slower.

## Exam triggers

| Question says… | Think… |
|---|---|
| reports show current data, no scheduled refresh | Direct Lake |
| what does a Direct Lake "refresh" actually do | framing — metadata-only pointer update |
| dashboards show inconsistent numbers during ETL | disable auto-update; reframe as last pipeline step |
| query exceeds guardrails / unsupported feature | falls back to DirectQuery |
| hour-long nightly model refresh, stale data between | Import mode symptom |

## Memory hooks
- **Import = photocopying the book. Direct Lake = reading the
  original.**
- **Framing = moving the bookmark, not re-copying the book.**
