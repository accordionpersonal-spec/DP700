# Staging in Dataflows Gen2 — Why It Exists
*DP-700 · supplement to "01 Introduction" (Core Concepts)*

## ⚡ The simple version (30 seconds)
- **Without staging**, the M engine does everything on **one machine**:
  pull all the data into memory, transform it there, write it out.
  Fine for small data, bad for big or complex work.
- **With staging**, Gen2 splits the job in two:
  1. **Land first** — dump the raw source data into a hidden internal
     Lakehouse (as Parquet/Delta). No transforming yet.
  2. **Then transform** — run the heavy steps on **Fabric's SQL
     compute** over that staged data, not the single-node M engine.
- Only the **final result** is written to your real destination.

> *Stop trying to do the work while carrying it — put the data down in
> Fabric first, then let Fabric's big engine do the work.*

---

## Example

A Dataflow Gen2 that:
- reads **20M sales rows** from Azure SQL
- reads **5M customer rows** from a CSV in ADLS
- **joins** them, then **groups by region**
- writes **~50 rows** into your Lakehouse

That join **can't fold** — no single source can do it, because the two
tables live in different systems.

| | What happens |
|---|---|
| **Staging OFF** | M engine downloads all 25M rows into its own memory, joins there, aggregates. Slow, likely chokes on memory. |
| **Staging ON** (default) | Both tables land raw in the staging Lakehouse. Join + group-by run as **SQL on Fabric compute**. Only the final 50 rows hit the destination. |

Same output. Hugely different execution.

---

## You can actually see it
Fabric creates hidden items in the workspace:
- **`DataflowsStagingLakehouse`**
- **`DataflowsStagingWarehouse`**

That's where staged data lands.

---

## Staging isn't always a win
It costs an extra **write-then-read hop**. If your query is small and
**fully foldable from a single source** — say just filtering one Azure
SQL table — staging is pure overhead. The source could have done the
whole thing in one SQL statement; instead you copy data into Fabric
and read it back.

| Situation | Staging |
|---|---|
| Big data, non-folding steps, multiple sources | **Leave it on** |
| Small, single source, fully folds to SQL | Turn it off |

Right-click a query → **Enable staging** to toggle it.

---

## Link to the folding gotcha
This is the other half of *Gotchas → Query Folding Limits* in the
Introduction. **Disable staging and folding becomes critical**, because
there's no Fabric compute to fall back on — non-folding steps get
processed in the M engine's local memory instead.
