# Query Folding — What It Is and Why It Matters
*DP-700 · supplement to "01 Introduction" (Gotchas) and "03 Explore Dataflows Gen2" (Exam Focus)*

## ⚡ The simple version (30 seconds)
**Folding = Power Query translating your clicks into the source's own
language (SQL), and making the source do the work** — instead of
dragging all the data over and doing it itself.

You don't turn it on. **It's automatic.** Your only job is to not break it.

---

## Example

50M-row `Orders` table in Azure SQL. You filter to 2024 and keep
3 columns. Result: 1M rows.

**It folds** — Power Query sends:
```sql
SELECT [OrderId], [OrderDate], [Amount]
FROM [dbo].[Orders]
WHERE [OrderDate] >= '2024-01-01'
```
The database filters it. **1M rows cross the network.**

**It doesn't fold** — Power Query sends:
```sql
SELECT * FROM [dbo].[Orders]
```
**All 50M rows cross the network** into the M engine's memory, and
*then* it filters down to 1M. Same answer, 50× the data movement.

---

## The misconception worth killing

> *"I selected the table, I see rows in the editor, I clicked through
> 4 steps one at a time — so it can't be folding, right?"*

**Wrong — and it's the opposite of what it looks like.**

- The rows you see are a **preview sample** (~1000 rows), pulled only
  to render the grid. It is *not* loading your table and *not*
  processing your steps locally.
- Each time you click a step, Power Query **rebuilds a query up to
  that step**, sends it to the source, and shows what comes back.
  The step-by-step feel is a **UI illusion**.
- At **refresh** time, all your steps get collapsed into **one single
  SQL statement**.

So a source → filter → concat query is probably folding already,
without you doing anything.

(This is the same point as *Gotchas → Data Preview vs. Full Execution*
in file 03.)

---

## Why it's important
- **Less data moved** — 1M rows vs 50M.
- **The database is better at it** — indexes, statistics, parallel
  execution. The M engine has none of that.
- **The M engine is one machine** — 50M rows may simply not fit in memory.
- **Folding breaks forward.** ⚠️ Once a step can't fold, **every step
  after it stops folding too**, even ones that normally would. One bad
  step early un-folds the whole query.

---

## What breaks it

| Usually folds | Usually breaks folding |
|---|---|
| Filter rows, remove columns | Add **Index column** |
| Rename, change type | `Table.Buffer` |
| Group by, sort | Merging **two different sources** |
| Join within the same source | M functions with no SQL equivalent |

**Rule of thumb — step order is the one thing you control:**
```
Source → filter rows → remove columns → [heavy/exotic stuff last]
```
Filter and drop columns **first**, while folding is still alive, so the
database shrinks the data before anything can break the chain.

---

## How to check (10 seconds)
1. Click a step in **Applied Steps** (Query Settings pane).
2. **Right-click** it → **View data source query**.
   *(Called **View Native Query** in Power BI Desktop — same thing.)*

- **SQL window opens** → that step folds. That SQL is literally what
  Fabric will send.
- **Greyed out** → folding stopped at or before that step.

Walk *up* the steps one at a time. Where it goes grey is your
breaking point.

---

## Ties back to staging
With staging **on**, non-folding steps get handed to Fabric's SQL
compute — there's a safety net. With staging **off**, there's no net:
anything that won't fold falls back to the single-node M engine's
local memory, which is where it gets slow or fails.
